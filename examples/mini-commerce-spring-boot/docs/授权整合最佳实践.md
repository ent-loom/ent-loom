# 商城实体授权：就地声明与实际复用

框架层的长期选择依据见[实体声明与授权基线风格](../../../docs/evolution/decisions/crud/实体声明与授权基线风格.md)。

实体专属授权放在 `@EntCrudGrant`，通用资源类别的稳定规则放在 [crud-policies.yml](../src/main/resources/crud-policies.yml)。是否提取基线按业务语义判断，不仅统计当前使用方数量；明显绑定具体实体字段或业务流程的规则就地声明。

## 分工

- `@EntEntity`、`@EntField`、`@EntRelation`：实体名称、字段事实和关系。
- `@EntCrudEntity`：基线选择、动作上限、字段上限、输入约束及 HTTP 暴露。
- `@EntCrudGrant`：当前实体的身份、操作、数据范围和字段白名单。
- YAML `grant-defaults`：商家和客户归属字段及管理员全局默认；实体显式管理员分支整体覆盖默认。
- Handler / Service：下单、取消等动态业务规则。

## 单实体规则就地声明

商品的上架条件、摘要字段和批量更新都属于商品自身规则：

```java
@EntCrudGrant(identities = "merchant", actions = {"view", "create", "update", "delete", "batch-update"})
@EntCrudGrant(identities = {"public", "customer"}, actions = "view", scope = EntCrudGrantScope.EQUAL,
    scopeField = "active", scopeValue = "true", inheritFields = false,
    fields = @EntCrudGrant.Fields({"id", "merchantId", "name", "price"}))
```

省略范围时按可信身份和全局归属字段限制。匿名必须显式指定 ALL 或 EQUAL；客户不会隐式继承匿名权限。公开字段使用白名单并关闭字段继承，防止新增字段扩大公开数据面。所有授权仍受实体动作及字段上限约束。

## 何时提取 YAML 基线

当前保留两种通用资源类别基线：

| 基线 | 语义 | 当前使用方 |
| --- | --- | --- |
| `customer-owned` | 客户维护所属资源，可用于银行卡、地址等 | CustomerBankCard |
| `merchant-managed-customer-readable` | 商家维护所属资源，客户只读本人记录 | CustomerLevel |

两者按可信身份分别使用默认 `customerId` / `merchantId` 范围，不包含实体专属字段白名单。字段限制仍由实体负责。银行卡、会员等级实体分别通过 `@EntCrudEntity(policy = "...")` 选择，不能同时声明 `@EntCrudGrant`。商家、客户主数据、商品、订单继续使用实体授权注解。

框架保留 `policy-overrides` 支持少量实体定制，选择基线遵循：

- 规则表达稳定的资源类别，有清晰的跨实体适用语义；允许暂时只有一个使用方。
- 选择基线后，实体只需要少量局部定制。
- 定制接近完整规则时，回到独立声明，不勉强复用。

仅有相同 CRUD 动作不足以证明业务策略可以复用。YAML 基线与实体 `@EntCrudGrant` 不混用；接口不承载授权。配置语义见框架[配置参考](../../../docs/guides/配置参考.md#yaml-授权基线与实体定制)。

## 当前业务边界

| 实体 | 边界 |
| --- | --- |
| Merchant | 商家维护本人，匿名和客户只读取商家摘要 |
| MerchantProduct | 商家维护自己的商品，匿名和客户只读取启用商品摘要 |
| MerchantArticle、MerchantWxConfig | 关闭通用 HTTP；商家和客户无独立授权入口，保留管理员原有全局授权 |
| Customer | 商家维护所属客户，客户维护本人，禁止删除 |
| CustomerBankCard | 客户维护所属银行卡 |
| CustomerLevel | 商家维护所属等级，客户读取本人的等级 |
| CommerceOrder | 客户下单，商家和客户读取、取消所属订单，管理员仅读取、取消 |

声明在启动期校验并冻结到统一策略注册表，请求继续走同一授权、JDBC 范围和字段投影执行链。

## 订单动作的最小分层

订单采用 `PlaceOrderHandler / CancelOrderHandler → CommerceOrderService → 数据访问`。Handler 负责动作接入，Service 统一承担下单、取消与事务，不另设应用服务、授权操作组件或订单范围解析器。

根订单通过 `AuthorizedActionContext.dao(...)` 复用框架授权范围：创建验证归属；取消先在授权范围内查询，再以 `status = CREATED` 附加条件执行仅修改状态的 Patch。状态判断与最终 SQL 条件同时保留，避免并发覆盖。客户、商品和订单明细仍由事务内的固定业务流程访问，不能把订单动作权限解释为这些实体的通用 CRUD 权限。
