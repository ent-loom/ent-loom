# 实体 DAO 统一读写与分页设计

> 状态：Proposal（设计取舍，非已实现能力）  
> 目标：先完成单表主键 CRUD、批量事务、明确更新语义和一种分页方式，再按真实业务扩展。

## 1. 较小闭环与较佳实践取舍

| 问题 | 首轮选择 | 原因与后续边界 |
| --- | --- | --- |
| 实体与 ById | 两类入口均向业务开放，共用治理规则 | 已有实体直接传实体；只有 ID 不必构造空壳实体或额外查询 |
| 更新与 null | 实体更新采用完整可写状态；局部修改使用强类型 Patch | 不默认忽略 null，避免清空无效；不引入脏检查 |
| 写入结果与失败 | 先固定影响行数、异常、版本与回填合同 | 属于正确性基础，投入小、收益高，不能留到实现末期 |
| 治理 | 按操作落实数据范围、逻辑删除、版本和审计规则 | 共用执行链不等于规则相同；专用 Repository 不天然绕过治理 |
| 分页 | 首轮按后台列表场景采用页码分页 | 支持跳页、实现较小；连续加载或深分页需求明确后另加游标合同 |
| Upsert | 暂不纳入通用 DAO | 唯一键冲突、并发、范围外记录、逻辑删除和版本语义复杂，不阻塞 CRUD |
| Java 兼容 | Core 公共 DTO 使用普通 Java 类 | 保持 Java 8 目标；完整 Reactor 仍使用 JDK 21 |

本轮调整设计合同，不要求同时建设所有扩展能力。业务授权、业务不变量和跨聚合事务仍由业务 Service 负责。

## 2. DAO 入口

以下为推荐合同示意；`UpdatePatch<T>` 表达强类型字段、字段值及可选预期版本，具体构造 API 在实现前确定。

```java
public interface EntityDao<T, ID> {
    Optional<T> findById(ID id);
    List<T> findAllById(Collection<ID> ids);

    ID insert(T entity);
    List<ID> insertAll(Collection<T> entities);

    int update(T entity);
    int updateById(T entity);
    int updateById(ID id, UpdatePatch<T> patch);
    int updateAll(Collection<T> entities);

    int delete(T entity);
    int deleteById(ID id);
    int deleteById(ID id, long expectedVersion);
    int deleteAll(Collection<T> entities);
}
```

- `update(entity)` 与 `updateById(entity)` 完全同义，均按主键更新；首轮不支持按任意唯一键更新。
- 实体入口与 ById 入口不改变授权、数据范围、逻辑删除和乐观锁要求。
- 示例版本类型为 `long`；启用乐观锁的实体更新、Patch 和删除必须携带预期版本。缺少版本在执行前拒绝，不能借无版本 ById 入口绕过校验。

## 3. 更新与写入结果

- 实体更新要求完整可写状态：所有可写业务字段参与更新，`null` 表示清空；部分加载或仅填部分字段的对象必须使用 Patch。
- Patch 区分“未声明”“赋值”“清空”；未声明字段保持原值，空 Patch 拒绝。框架提供类型化字段入口，不要求业务拼字段字符串或框架协议。
- 主键、租户归属、逻辑删除标志、版本和框架审计字段不属于普通可写字段；由身份条件或对应框架规则处理。
- `insert` 返回主键，并回填框架生成的主键、版本和审计字段；更新返回匹配并成功执行的记录数，不承诺返回数据库完整快照。
- 更新命中但字段值相同视为成功；实现需消除驱动“匹配行数/实际变更行数”配置差异，不能将未变更误判为不存在。
- 更新未命中时抛统一写入失败异常；带版本写入未命中按并发写入失败处理，不通过无范围查询区分或泄露记录存在性。
- 成功更新回填框架维护的新版本和审计字段；数据库默认值、触发器结果等完整状态按需重新查询。
- 唯一键冲突、参数错误、并发写入失败由框架分类异常表达，业务自行映射业务提示。
- 事务回滚不保证恢复已回填的内存对象；失败后不得将这些对象当作已提交状态继续使用。

## 4. 批量与删除

- 空集合直接返回空结果或 0；首轮逐条执行并分块管理资源，不承诺单条 SQL。
- 批量写入默认加入已有事务，无事务时创建事务；任一失败整体回滚，不逐块提交。设定批量数量上限，超限拒绝。
- `findAllById` 按输入 ID 首次出现的顺序去重返回；未命中项省略。
- `insertAll` 按输入顺序返回主键并回填实体；`updateAll`、`deleteAll` 返回成功处理总数。重复写入身份或声明的冲突键在执行前拒绝，数据库唯一约束仍是最终保障。
- 删除附加数据范围和未删除条件；配置逻辑删除时执行逻辑删除。
- 未启用乐观锁的删除允许幂等：不存在、不可见或已删除均返回 0。启用乐观锁时必须携带版本，未命中抛并发写入失败异常，批量整体回滚。
- 物理删除交给职责明确的专用 Repository，仍默认受数据范围等适用治理约束。

## 5. 首轮分页合同

分页由 `@EntQuery` 显式业务查询方法承接，业务声明筛选条件与返回类型，框架统一处理分页。`EntityDao` 保留基础 CRUD，不新增通用分页方法，也不提前抽取 `EntityQueryDao`。首轮使用独立 `PageQuery` 参数与业务筛选参数组合，实施方案见第 8 节。

| 对象 | 字段 |
| --- | --- |
| `PageQuery` | `pageNumber`（从 1 开始）、`pageSize`、`sorts`、`countMode` |
| `PageResult<T>` | `items`、`pageNumber`、`pageSize`、`hasNext`、`total`（未计数时为 null） |

```java
public enum CountMode {
    NONE,   // 默认，不查询总数
    ALWAYS  // 明确查询总数
}
```

- 页码与页大小在调用期校验；框架设置页大小和最大偏移上限，超限拒绝并提示使用专用查询。
- 排序字段白名单校验，追加主键作为唯一排序依据；框架绑定分页参数，业务不拼接 SQL。
- 多取一条判定 `hasNext`；计数使用相同筛选与治理条件，不包含分页限制。默认不承诺列表与总数的快照一致性。
- 首轮支持单表实体或明确 DTO；复杂 JOIN、聚合、跨实体查询交给专用 Repository。
- 游标分页后续使用独立请求/结果合同，届时明确空值排序、游标与查询条件绑定及并发一致性边界；追加主键不等于并发下不重不漏。

## 6. 统一治理边界

- 通用 DAO 的基础、批量和查询能力共用执行链，并按操作应用规则：插入校验/注入数据归属，更新限制可写字段与记录范围，删除执行删除策略与版本校验。
- 普通专用 Repository 同样遵守适用治理规则；复杂 SQL 不是绕过治理的理由。
- 自定义 SQL 只支持可验证的受限语法；无法验证治理条件时启动失败。首轮不扩展为任意 SQL 分析器。
- 用户参数不能关闭或放宽治理。确有维护需求时，另设明确授权、独立入口和审计的维护能力，不提供普通业务逃生开关。

## 7. 实现顺序与验收

1. 固定更新、Patch、写入失败与治理合同，落实开放的实体/ById 单条 CRUD。
2. 复用单条规则完成批量事务，验证空集合、重复身份和失败回滚。
3. 实现页码分页与可选计数，补充后台列表和批量读取示例。
4. 重点验证清空字段、受保护字段、版本缺失/冲突、范围隔离、逻辑删除、分页上限及 Java 兼容边界。

暂不纳入：通用 Upsert、游标分页、关系导航、脏检查、级联写入、任意动态 SQL、跨实体 JOIN/复杂聚合。后续扩展必须由真实业务场景驱动，并先定义语义再扩充 API。


## 8. `@EntQuery` 页码分页实施方案

> 状态：已实施（单表页码分页与可选计数）；决策日期：2026-09-21。<br />
> 实现入口：`JdbcEntityDaoCustomMethodExecutor`；`EntityDao` 仍只保留基础 CRUD。<br />
> 关联文档：[实体 DAO 自定义方法](./实体DAO自定义方法.md)。

### 8.1 实现思路

较小闭环以一个真实单表业务列表为验收入口：业务定义查询，框架复用分页和治理机制。

```java
public interface OrderDao extends EntityDao<Order, Long> {
    /** 按订单状态分页查询。 */
    @EntQuery("SELECT * FROM t_order WHERE status = :status")
    PageResult<Order> findByStatus(OrderStatus status, PageQuery pageQuery);
}
```

- 复用现有自定义查询的受限 SQL 解析、命名参数绑定、结果映射及治理执行链，不另建分页执行旁路。
- 首轮只支持现有受限语法内的单表实体或明确 DTO 查询；业务不编写 `LIMIT/OFFSET` 或计数 SQL。
- 复用现有 `PageQuery`、`PageResult<T>` 与 `CountMode` 模型；`CountMode.NONE` 默认不计数，`ALWAYS` 查询精确总数。
- Core 公共模型保持 Java 8 兼容，完整构建使用 JDK 21。
- 默认分页页大小上限为 200、偏移上限为 1,000,000，可通过 `ent.loom.crud.dao.pagination.max-page-size` 和
  `ent.loom.crud.dao.pagination.max-offset` 配置；后续由连续加载或深分页需求驱动独立游标合同。
- 通用动态筛选入口、`DISTINCT`、复杂 JOIN、聚合和任意 SQL 自动计数不纳入本轮。

### 8.2 实施清单

- [x] **启动期合同校验**：识别 `PageResult<T>` 与唯一 `PageQuery` 参数；分页参数不作为普通 SQL 命名参数绑定；拒绝不匹配的方法签名及业务 SQL 自带分页子句。
- [x] **分页模型**：落实页码从 1 开始、页大小、排序、计数模式，以及数据、页码、页大小、`hasNext`、可空总数的返回语义。
- [x] **分页限制**：调用期校验分页参数非空、合法页码、页大小上限与最大偏移；使用 long 计算偏移，避免整数溢出。
- [x] **排序规则**：请求排序覆盖 SQL 中的排序；请求字段使用实体可排序字段白名单；无请求排序时保留 SQL 排序，无排序时默认主键升序，未包含主键时追加主键。实体和 DTO 投影均复用该校验。
- [x] **查询执行**：解析阶段生成单表 SELECT 的数据片段、计数片段和排序片段，治理条件生效后由框架按方言生成分页 SQL；多取一条判断 `hasNext`，返回时移除额外记录。
- [x] **可选计数**：`CountMode.NONE` 默认不查询总数；`ALWAYS` 使用相同筛选、参数与治理条件生成结构化计数 SQL，移除排序和分页；不承诺数据与总数快照一致。
- [x] **业务示例**：在 JDBC 自定义 DAO 测试中提供带筛选条件的 `@EntQuery` 分页方法与实体列表调用。
- [x] **必要测试**：覆盖首末页、越界空页、可选计数、稳定排序、非法参数与声明、范围隔离、逻辑删除、实体映射，以及原有非分页查询回归。
- [x] **集成验证**：补充 Spring `EntDao` 代理真实分页调用，并在既有 MySQL 8 integration profile 中验证 `LIMIT/OFFSET`、计数和治理条件。
- [x] **构建验证**：使用 JDK 21 运行 JDBC 模块测试及相关检查。
- [x] **文档同步**：本文与《实体 DAO 自定义方法》已同步分页能力状态与边界。

### 8.3 验收标准

业务只需声明单表查询并传入分页参数，即可获得受统一治理约束的分页结果，无须自行编写分页和计数 SQL；原有非分页自定义查询正常工作。`DISTINCT`、聚合、JOIN、游标和任意动态 SQL 仍需使用专用 Repository。
