# 测试策略与验收分层

> 性质：Core Contract
> 状态：Current
> 最近核验：2026-08-25

本文定义 ent-loom 的全局测试分层、模块责任和阶段门禁，作为后续开发的通用验收基线。它回答“每一类边界应该在哪里验证”；具体模块的测试类、命令、当前事实和阶段证据仍以对应模块路线图为准。

## 使用边界

测试策略与路线图同步维护，但两者职责不同：

- 本文规定 L1-L5 的测试含义、进入条件和禁止跨越的边界。
- 领域路线图规定当前只做哪一个阶段，以及该阶段必须留下的代码、测试和验收证据。
- 模块 README 只描述模块定位和依赖方向，不替代测试门禁。
- Architecture 只记录已经稳定的边界，不把尚未排期的后续能力写成当前事实。

“同步进行”指现在就把测试策略、证据格式和阶段映射定下来，并随每个阶段补齐对应测试；不表示在 E1 中提前实现实体扫描、真实数据库执行或业务全链路。

## 核心原则

1. 模块测试保证“自己正确”，消费者测试保证“别人能接入”，集成测试保证“能连接真实基础设施”，全链路测试只验证最小主路径。
2. 测试依赖和测试装配不能进入 Core 的运行时依赖；业务模拟不能反向成为框架模块的生产依赖。
3. 可拔插能力必须在成功、空输入、异常、重复调用和不可变结果这几个共同维度上验证；具体 SPI 再增加自己的领域语义。
4. 测试层级从低到高逐步扩大环境和组合范围。低层失败时，不用高层测试掩盖合同问题。
5. 一个测试只验证一个主要边界。跨模块测试验证组合关系，不重复覆盖每个模块内部算法。
6. 每一阶段都必须记录范围、命令、测试类、环境、结果和明确未完成项，避免“测试通过”失去上下文。

## 测试分层

```mermaid
flowchart TB
    l1["L1 模块单测\n纯逻辑 / 合同 / 边界"]
    l2["L2 SPI 契约测试\nFake 实现 / 结果 / 异常"]
    l3["L3 消费者模拟\n只依赖公开构件"]
    l4["L4 集成测试\nSpring / JDBC / MySQL 8"]
    l5["L5 全链路验收\nDDL / CRUD / DOC / UI"]

    l1 --> l2 --> l3 --> l4 --> l5
```

### L1：模块内单测与边界测试

位置：各模块自己的 `src/test`。

覆盖模块内部的纯 Java 逻辑、Runtime Model、状态转换、SQL 生成、默认值、校验、异常和不可变集合。Core 模块同时使用 ArchUnit 或等价检查，验证禁止依赖没有从 POM 或字节码边界回流。

典型覆盖：

- `annotations`：注解默认值、组合声明和编译期可用性。
- `api`：构造参数、空输入、枚举边界、不可变结果和兼容性。
- `core`：纯业务算法、稳定顺序、状态矩阵、异常分类和模块边界。
- `bootstrap`：显式类列表到 Runtime Model 的解析。
- `spring`：包扫描、Spring Bean 和配置装配。
- `starter`：自动配置开关、缺省 Bean 和禁用时不执行。
- `adapter`：来源映射、优先级、冲突和目标 Runtime Model。

L1 是每次提交的最小反馈闭环，不要求启动 Spring 或数据库。

### L2：SPI 契约测试

位置：优先放在 SPI 所属模块；多实现共享的公共断言可放在独立测试支持目录，但不发布为生产 API。

每个可拔插接口至少验证以下矩阵：

| 场景 | 验证重点 |
|---|---|
| 正常输入 | 调用顺序、结果字段和成功状态 |
| 空输入 | 是否无副作用、是否返回空集合或明确结果 |
| 非法输入 | fail-fast 位置、异常类型和诊断信息 |
| 执行异常 | generated、executed、errors 或等价结果的区分 |
| 重复调用 | 幂等性、冻结状态和是否重复注册 / 执行 |
| Fake 实现 | 消费者可以替换实现，不依赖具体框架或数据库 |

Fake 只模拟可观察的 SPI 行为，不复制生产实现的内部算法。例如 DDL 使用 fake `QueryStrategy` 和 `SqlExecutor` 验证编排；不在 fake 中模拟 MySQL 方言解析。

### L3：独立消费者模拟

位置：建议建立独立的 `ent-loom-tests` 聚合，按场景拆分消费者测试模块：

```text
ent-loom-tests/
├── ent-loom-ddl-consumer-test
├── ent-loom-cross-module-test
└── ent-loom-e2e-test
```

消费者模块模拟真实业务项目，只依赖公开构件和公开接口：

```mermaid
flowchart LR
    business["业务实体 / 业务约定"]
    consumer["消费者测试模块"]
    api["公开 API / Annotations"]
    core["公开 Core 能力"]
    fake["Fake SPI"]
    result["可观察结果"]

    business --> consumer
    consumer --> api
    consumer --> core
    consumer --> fake
    api --> result
    core --> result
    fake --> result
```

消费者测试必须遵守：

- 不引用 `core` 的包内实现、测试类或内部工具。
- 不把 Spring、Servlet、Starter 作为 Core 消费合同的隐含前提。
- 不直接访问测试目录中的 fixture；业务 fixture 应放在消费者模块内部。
- 至少验证一次“只使用公开构件即可编译并完成最小调用”。
- 跨模块测试只验证 Adapter 和公开 Runtime Model 的组合，不替代各模块 L1。

独立消费者模块不是生产模块，也不是万能 Demo；它的职责是尽早发现公共 API 漂移和不真实的接入假设。

### L4：基础设施集成测试

位置：Spring、JDBC 和数据库相关模块，使用独立 Maven profile 或专用测试模块。

分层验证真实基础设施：

- Spring：上下文启动、条件装配、配置绑定和关闭开关。
- JDBC：事务、查询、执行异常和资源释放。
- MySQL 8：建库、建表、字段类型、默认值、索引和实际执行结果。
- Testcontainers：提供可重复的 MySQL 8 环境，测试结束后销毁容器。

H2 可以作为快速辅助数据库，但不能替代 MySQL 8。凡是涉及 MySQL 方言、DDL 默认值、索引或标识符语义的测试，最终必须有 MySQL 8 证据。

L4 不应成为每次提交的默认阻塞项，除非变更直接触及对应集成层；它至少应在合并、发布或夜间门禁中执行。

### L5：最小全链路验收

只选择一个简单实体，验证最短主链：

```mermaid
sequenceDiagram
    participant B as 业务实体
    participant M as Runtime Model
    participant D as DDL
    participant C as CRUD
    participant O as DOC / UI
    participant DB as MySQL 8

    B->>M: 声明 / 解析 / 归一化
    M->>D: 生成结构计划
    D->>DB: 建表并验证结构
    B->>C: 发起最小 CRUD 调用
    C->>DB: 写入 / 查询
    M->>O: 投影文档和 UI 契约
    O-->>B: 返回可观察模型
```

L5 只证明跨领域组合成立，不承担所有异常矩阵、所有数据库类型和所有业务权限场景。复杂关系、批量操作、权限和迁移风险应留在对应模块或集成层测试。

## DDL 独立测试模块定位

| 测试模块 | 层级 | 核心责任 | 明确边界 |
|---|---|---|---|
| `ent-loom-ddl-consumer-test` | L3 消费者模拟 | 模拟业务方仅使用公开 Annotations、API 与 Bootstrap 完成最小实体接入。 | 使用 Fake SPI，不验证 Spring、JDBC 或真实数据库。 |
| `ent-loom-ddl-mysql-integration-test` | L4 基础设施集成 | 验证 DDL Starter 与 Spring JDBC 在 MySQL 8 中实际建库、建表和读取结构。 | 只覆盖 DDL 专项，不验证 Meta、CRUD、DOC、UI 组合。 |
| `ent-loom-e5-static-test` | L5 最小全链路验收 | 以同一 `CustomerProfile` 验证 Meta、DDL、CRUD、DOC、UI 的最小组合；包含 MySQL DDL 与 H2 + MockMvc CRUD 入口。 | 只覆盖一个无关系实体，不替代 DDL 专项集成或复杂业务验收。 |

两个 MySQL 用例并不重复：`ent-loom-ddl-mysql-integration-test` 证明 DDL 自身可在真实 MySQL 中执行；`ent-loom-e5-static-test` 中的 MySQL 用例证明 DDL 可作为同一业务实体全链路的一环工作。

## 阶段与测试层级映射

阶段推进不等于一次性启用所有测试层级。每个阶段只对表中“本阶段门禁”负责，后续层级先记录设计和启动条件。

| DDL 阶段 | 本阶段必须完成 | 本阶段不提前完成 | 最低验收层级 |
|---|---|---|---|
| E1 Core 建表 | 元数据合同、稳定 CREATE SQL、执行编排、Fake SPI、Core 边界 | 实体扫描、Spring JDBC、真实 MySQL、CRUD/DOC/UI | L1 + L2 |
| E2 发现与实际执行 | 显式 / 包扫描、Spring 配置接入、真实执行器、一个 MySQL 8 建表证据 | ALTER 差异、Meta Adapter、跨领域业务主链 | L1 + L2 + L3 + 定向 L4 |
| E3 结构差异 | 表结构读取、差异计划、安全 ALTER、失败结果 | Meta 语义扩张、CRUD/DOC/UI 全链路 | L1 + L2 + 定向 L4 |
| E4 Meta -> DDL | Meta 到 DDL 的来源、优先级、冲突和适配合同 | 真实全领域业务演示 | L1 + L2 + L3 |
| E5 实体全链路 | 一个简单实体贯通 DDL、CRUD、DOC、UI | 复杂关系和业务权限扩展 | L4 + L5 |

“同步建设测试策略”只表示提前固化验证方式，不把后续阶段的实现倒灌到当前阶段。E1 的完成证据只需要 L1/L2；E2 才引入消费者模拟和定向 MySQL 8 集成；E5 才做跨 DDL、CRUD、DOC、UI 的全链路验收。

## DDL 实体全链路验收入口

DDL E1-E5 已完成，唯一任务顺序和验收结论维护在 [DDL 实施清单](../../evolution/roadmap/ddl/DDL实施清单.md)。E5 以 `CustomerProfile` 固化最小 L4/L5 入口：

- `E5EntityRuntimeStaticAcceptanceTest` 验证 Meta、DDL、CRUD、DOC、UI Runtime Model 的公开契约投影。
- `E5MysqlDdlAcceptanceTest` 通过专用 `mysql-integration` profile 在隔离 MySQL 8 中创建随机 schema，验证字段、主键、自增和唯一索引。
- `E5CrudMvcAcceptanceTest` 以 H2 和 MockMvc 验证 `create`、`detail`、`update`、再次 `detail`、`delete`，不启动真实 HTTP 服务。

该验收不引入 Testcontainers、复杂关系或业务权限；具体前置条件、命令和边界见 [实体全链路验收](../../guides/ddl/实体全链路验收.md)。后续 DDL 阶段未排期。

## 模块与能力测试责任

| 能力 | L1 重点 | L2 / L3 重点 | L4 / L5 重点 |
|---|---|---|---|
| DDL | 元数据合同、MySQL SQL、执行结果和 Core 边界 | Fake 查询 / 执行器、消费者实体接入 | MySQL 8 实际建表和 E2E 主链 |
| CRUD | Spec、合法矩阵、Engine、治理和结果 | Fake Repository / Handler、公开 API 接入 | Spring JDBC、HTTP 和事务 |
| Meta | Descriptor、Resolver、诊断和冻结模型 | Native-only、Meta-only、Meta + Module | Starter 收集与跨模块投影 |
| Adapter | 来源、优先级、冲突和目标模型 | Meta -> DDL / CRUD / DOC / UI 消费者 | 组合装配和完整实体投影 |
| Spring / Starter | 配置对象和条件分支 | 缺省 Bean、替换 Bean、关闭开关 | 真实应用上下文启动 |
| DOC / UI | Runtime Model 和输出合同 | 业务字段展示 / 编辑接入 | 与实体、CRUD、Meta 组合验收 |

## 测试模块边界

```mermaid
flowchart LR
    module["模块 L1 测试"]
    contract["SPI L2 测试"]
    consumer["消费者 L3 测试"]
    integration["集成 L4 测试"]
    e2e["全链路 L5 测试"]
    production["生产构件"]

    module --> production
    contract --> production
    consumer --> production
    integration --> production
    e2e --> production
    module -. "禁止生产依赖" .-> consumer
```

约束如下：

1. 生产模块不得依赖任何测试模块。
2. L1/L2 测试可以依赖测试框架和 ArchUnit，但这些依赖必须是 `test` scope。
3. L3 消费者测试只依赖发布视角的公开 artifact；可以依赖 fake，但 fake 不进入生产类路径。
4. L4 可以依赖 Spring、JDBC、Testcontainers 和数据库驱动，但必须与 Core 测试入口隔离。
5. L5 可以依赖多个公开模块，但不能通过反射访问内部实现来“拼接”结果。

只有在出现真实消费者、稳定测试边界和可观察收益后，才新增独立测试 artifact；不存在真实边界时优先增加模块内测试和测试 fixture，避免创建空泛的测试占位模块。

## CI 门禁

```mermaid
flowchart LR
    commit["提交检查"] --> merge["合并检查"]
    merge --> release["发布 / 夜间检查"]

    commit --> c1["受影响模块 test\nL1 + L2 + 边界"]
    merge --> c2["完整 Reactor test\n消费者测试"]
    release --> c3["Spring / JDBC 集成\nTestcontainers MySQL 8"]
    release --> c4["最小全链路验收"]
```

- 提交检查：固定 JDK 21、Maven Wrapper、受影响模块测试和架构边界测试。
- 合并检查：完整 Maven Reactor 测试、独立消费者测试和跨模块 Adapter 测试。
- 发布 / 夜间检查：Spring 上下文、JDBC、Testcontainers MySQL 8 和最小全链路验收。
- 测试失败必须保留命令、测试类、环境和失败结果；不能只记录“构建失败”。

每个阶段的验收证据统一使用以下字段：

```text
范围：本次实现的阶段 / 小项
命令：完整可复制的命令和 JDK
测试：测试模块、测试类或关键场景
环境：是否依赖 Spring、JDBC、MySQL 8、Testcontainers
结果：通过数、失败数、错误数
边界：已验证的依赖 / 装配 / 结果合同
未完成：明确留给后续阶段的能力
```

## 当前落地顺序

```mermaid
flowchart LR
    ddl["DDL E1\nCore 单测 + SPI Fake"] --> ddlConsumer["DDL E2\n消费者实体 + 实际执行"]
    ddlConsumer --> diff["DDL E3\n差异计划"]
    diff --> adapter["DDL E4\nMeta Adapter"]
    adapter --> chain["DDL E5\n全链路实体"]
```

当前采用“先较小闭环，再扩大环境”的顺序；DDL E1-E5 已按以下路径完成：

1. 先在各 Core 完成 L1 和边界守卫。
2. 再为每个 SPI 增加 fake 实现及 L2 结果合同。
3. 出现稳定公开 API 后，新增对应消费者模拟模块完成 L3。
4. E2 完成发现、Spring 装配和执行合同后，启用定向 MySQL 8 集成测试。
5. E5 用一个简单实体完成 DDL、CRUD、DOC、UI 的 L5 验收。

当前 DDL 的具体测试命令和证据见 [DDL 实施清单](../../evolution/roadmap/ddl/DDL实施清单.md)，实体示例见 [实体全链路验收](../../guides/ddl/实体全链路验收.md)。
