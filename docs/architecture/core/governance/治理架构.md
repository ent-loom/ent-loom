# CRUD 权限治理架构

> 状态：Current

本文描述 CRUD 内部的业务实体访问治理。Meta、DDL、DOC、UI 按各自职责设计，见[模块职责与宿主接入](../组件边界与依赖规则.md#模块职责与宿主接入)。

治理是内置 CRUD Gateway 的强制边界：先解析主体、权限和数据范围，再进入路由或执行器。框架提供
fail-closed 默认实现，业务通常需要替换真实主体、权限、范围和审计 SPI。

推荐阅读：

1. [治理 Pipeline](治理流水线.md)：CRUD 各操作域必须遵守的阶段、fail-closed 和扩展边界。
2. [治理 Core 实现](治理核心架构.md)：默认实现、范围交集、保留键与审计语义。
3. [执行上下文与主体](../subject/执行上下文与主体.md)：同步上下文和异步快照边界。
4. [业务接入模板](../../../guides/crud/业务集成模板.md)：业务实现和装配方式。

默认 SQL 如何应用最终治理范围见 [Default Engine](../../components/crud/默认引擎.md)。

## 已验收的按次授权 JDBC 查询

`JdbcAuthorizedQueryExecutor` 提供显式可信 `VisitorContext` 的普通根实体 LIST/PAGE 执行入口，每次经业务操作映射和统一内核重新授权后执行范围约束。输出限于 `CrudRecord`；默认投影只取允许返回的普通字段，显式投影、筛选和排序分别校验字段用途，输出再次按投影白名单构建。列表、精确计数与无计数分页复用标准 JDBC 编译和执行，逻辑删除、旧治理范围及调用方条件只收窄新授权范围。

Starter 在 JDBC、安全守卫和审计能力齐备时注册该执行器，并将内置 `QueryGateway.list/page` 的业务授权路径接入它。实体选择 `EntityPolicyBinding` 或 `@EntCrudPolicy` 即建立资源级新治理边界；此后缺少可信作用域也必须拒绝，不能退回旧治理。`@EntAccess` 的可信作用域内，未绑定资源同样不能借旧链放行。未绑定且无可信作用域的既有资源继续原治理。

每个 MVC Handler 独立保存准入和同步作用域；嵌套 forward 结束后恢复外层，未声明 Handler 屏蔽外层身份。声明式 MVC Callable 的工作线程只保留“必须授权”标记，不携带主体或身份，未绑定资源也不能退回旧链；其他异步执行以资源级策略绑定为边界。需要执行时必须通过可信来源重新准入并显式打开作用域。按次查询复用 `CrudGovernanceAuditRecorder`，保留访问者和完整授权结果，分别记录拒绝、实际执行失败以及投影完成后的成功；公共分支的实际认证主体只用于审计。

场景、关联、多实体、实体/DTO 输出、时间简写及旧 grantedScope 在 SQL 前拒绝；脱敏和 DAO 的批量写入适配仍待后续验收。G4.4 已在同一入口接通 `findOne/detail`，要求主键 `EQ` 目标并保留可空/必须存在语义。G4.5 接通 `CommandGateway` 的根实体单目标 `UPDATE/DELETE`：每次按目标重新授权，`WRITE` 字段白名单、参数化授权范围、逻辑删除和单事务边界在 JDBC 执行前后生效；批量、归属变更、自动填充和无事务能力保持拒绝，影响行数必须严格为 1。G4.6 在受治理访问作用域内对 Starter DAO 代理、标准 JDBC DAO 工厂及自定义 DAO 方法增加统一门禁；旧 `EntityAccessScope` 不能替代按次业务授权，批量事务、归属变更和自动填充继续在存储访问前拒绝。G4.7 增加 `EntityDaoAuthorizationContext` 和 `EntityDaoFactory.scopedAuthorized`，要求消费方保留同一授权请求、访问者、业务操作、目标和规范资源；未完成存储适配的工厂默认拒绝，不能回退 `scoped`。G4.8 标准 JDBC DAO 仅开放单目标 `findById`，将授权范围、逻辑未删除、主键目标和 `RETURN` 字段白名单编译进参数化 SQL；批量、写入、自定义方法及目标不一致保持拒绝。G4.9 将单目标 DAO 读取的成功、授权拒绝及 SQL/映射失败接入统一治理审计，Starter 标准 JDBC 工厂装配现有 `CrudGovernanceAuditRecorder`。G4.10 提供 `EntityDaoAuthorizationProvider`，由业务方显式提交可信访问者、业务操作和目标 ID，经 `BusinessAuthorizationService` 签发允许结果后才创建按次授权 DAO；拒绝结果不会进入工厂。G4.11 在同一按次上下文中开放无 `version` 实体的单目标 DAO `updateById/deleteById`：要求 `update/delete` 操作码、`WRITE` 字段能力、目标主键一致、参数化范围及逻辑删除条件，单事务执行且影响行数必须为 1。G4.12 为带 `version` 实体增加预期版本条件、成功自增回填和带版本删除；过期版本、缺版本、无事务、批量、归属变更、自动填充和自定义方法继续拒绝。G4.13 冻结按次授权 DAO 的单目标边界：授权上下文必须绑定单一目标，批量查询/新增/更新/删除在存储访问前拒绝，并明确逐目标授权、范围交集、事务回滚和逐目标审计合同尚未建立。G4.14 将未适配 DAO 形状的拒绝接入统一治理审计，查询和命令分别记录 `UNSUPPORTED_OPERATION`，审计失败不覆盖原拒绝。G4.15 用 JDBC 测试锁定审计记录器故障隔离：不支持形状仍返回原 `PermissionDeniedException`，不执行 SQL。G4.16 在 Core 建立逐目标授权批次输入：每个目标独立授权并保留自己的范围/字段能力，要求同一访问者、同一业务操作、目标唯一且按输入顺序保存；该上下文不提供存储、事务或回滚语义，标准 JDBC 继续拒绝批量。G4.17 为批次输入增加 Core 默认 500 个目标上限，并在授权调用前校验集合大小、空目标和重复目标；该上限只限制授权输入规模，不授予批量存储、事务或回滚能力。实际证据见[业务实体访问治理实施记录 G4.17](../../../evolution/roadmap/crud/业务实体访问治理/实施记录.md#40-g417-限制逐目标授权批次输入规模)。

G4.18 按目标保留显式 `ALL`、`NONE` 和受限范围，并将统一收窄条件分别取交集；不同目标的范围不相互 AND/OR，`NONE` 仅表示该目标无数据，不把它改写成整体授权拒绝。实际证据见[业务实体访问治理实施记录 G4.18](../../../evolution/roadmap/crud/业务实体访问治理/实施记录.md#41-g418-固化逐目标范围与无数据语义)。

G4.19 增加 `EntityDaoBatchExecutionResult`，以 `SUCCEEDED`、`NO_DATA`、`VERSION_CONFLICT` 和 `EXECUTION_FAILED` 按授权目标逐项返回结果；结果集合必须保持目标数量、ID 和顺序一致，拒绝目标不进入集合。该类型只描述逐目标观测结果，不表示事务提交、回滚或部分成功。G4.20 为结果增加 `ALL_OR_NOTHING` 默认声明，只有显式 `EXPLICIT_PARTIAL` 才能表达部分结果意图；G4.21 拒绝全量原子结果中的成功/失败混合状态；G4.22 要求事务执行器实现 `CrudBatchTransactionCapability` 后才能声明批量原子性，未声明的执行器默认拒绝，当前 JDBC 执行器只支持 `ALL_OR_NOTHING`；G4.23 已将能力检查接入 JDBC DAO 批量写入和显式主键命令批量入口，能力不足时在事务回调和 SQL 前拒绝；G4.24 增加 `EntityDaoBatch` 只读合同，Provider 按目标授权后由 JDBC Factory 构造目标 DAO，主键必须属于已授权目标并分别消费其范围；G4.25 增加 `readById` 逐目标只读结果，要求主键覆盖全部授权目标，分别返回 `SUCCEEDED`、`NO_DATA` 或 `EXECUTION_FAILED`，成功/失败混合时显式声明 `EXPLICIT_PARTIAL`；G4.26 由 Core 校验值 Map 仅包含 `SUCCEEDED` 目标、每个成功目标都有值，并按授权顺序重建不可变 Map；G4.27 要求 `readById` 的空、数量不一致、重复和未授权主键在 SQL 前拒绝；G4.28 保留逐目标审计关联，每个目标使用自己的原授权请求和 `SUCCESS`/`EXECUTION_FAILED` 结果，不生成聚合审计事件；G4.29 要求同一批次的每个目标分别消费自己的 `RETURN` 字段能力，未授权字段不得进入实体结果；批量写入、版本结果、事务回滚和聚合审计仍未开放。这些合同不替代真实事务执行器。实际证据见[业务实体访问治理实施记录 G4.29](../../../evolution/roadmap/crud/业务实体访问治理/实施记录.md#52-g429-验证逐目标返回字段隔离)。
