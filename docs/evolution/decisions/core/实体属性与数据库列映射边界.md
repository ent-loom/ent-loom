# 实体属性与数据库列映射边界

> 状态：Accepted（属性识别与单列映射闭环已实施，JSON／转换器扩展待实施）
> 日期：2026-09-26
> 最近核验：2026-09-27
> 范围：Meta、CRUD、DDL、DOC 的实体属性识别与投影
> 实施跟踪：[Meta 路线图](../../roadmap/meta/index.md)

## 决策

实体可以直接携带关联对象、实体列表及临时展示值。框架按 Java 类型推断默认列映射，允许显式覆盖，并校验映射是否受支持。

业务属性、数据库列映射和关系声明分别表达独立事实：

- 业务属性：Java 属性名称、类型、中文名称、说明等。
- 数据库列映射：属性是否映射当前实体表的列，以及对应的存储转换。
- 关系声明：源字段、目标实体、目标字段、基数等关联信息。

`@EntField` 提供业务元数据；添加名称或说明不能强制属性进入数据库列集合。非列属性仍可以参与业务装配与文档描述。关系加载、关联筛选和聚合写入遵循 CRUD 各自的执行契约。

## 默认规则

“单列值类型”指当前引擎明确支持直接映射到一列的 Java 类型，不能仅用 `Class.isPrimitive()`、任意 `Number` 子类或包名前缀判断。

| 属性情况 | 默认列映射 | 处理规则 |
|---|---|---|
| 支持的基本类型、包装类、String、BigDecimal、枚举和日期时间类型 | 是 | 使用已支持的读写与 DDL 类型映射 |
| 已识别的实体对象、实体集合 | 否 | 保留属性信息，允许业务代码装配 |
| 普通 POJO、Map、其他集合和未支持的数组类型 | 否 | 保留属性信息，需要单列存储时显式配置映射 |
| `byte[]` 等特殊值类型 | 由支持清单决定 | 引擎支持二进制列时可作为单列值；不能按“数组”一律排除 |
| 显式配置非持久化的标量 | 否 | 用于计算值、展示值等 |
| 显式配置 JSON／转换器的复杂属性 | 是，须通过校验 | 读写转换及适用的 DDL 映射必须可解析 |

默认类型集合以 `EntityProperty.isSingleColumnType` 为准：数值基本类型及包装类、布尔、字符、String、BigDecimal、BigInteger、枚举、LocalDate、LocalDateTime、LocalTime、Instant、Date、SQL Date/Time/Timestamp 和 `byte[]`。不使用任意 Number 或 Date 子类作为列资格判断。

当前 JDBC DAO 的 `LocalTime` 单列存储仅支持秒精度；含小数秒的值在执行 SQL 前拒绝，不自动截断或舍入。微秒支持需统一调整 DDL 精度、参数绑定和结果读取，留待后续扩展。

显式配置优先于默认推断，但不能绕过能力校验。明确要求持久化却缺少类型映射或转换器时，应在模型注册阶段报错；不能悄悄排除属性或在执行 SQL 时才失败。显式配置互相冲突时，按统一元数据裁决规则处理并提供字段位置诊断。

静态字段和合成字段不进入业务属性模型；同名属性按子类优先识别。Java `transient` 属性保留业务描述，默认不映射列，显式要求持久化时拒绝。它涉及 Java 序列化语义，推荐使用下述公共注解意图表达业务非持久化。

## 业务用法

以下为当前支持的使用方式。

### 主实体携带明细

```java
@EntField("订单明细")
private List<OrderItem> orderItemList;
```

该属性不映射订单表列，不需要重复添加 `exist = false`。业务 Handler 可以查询明细后自行赋值。仅凭 `List<OrderItem>` 不推断关联外键、不触发自动加载，也不触发级联保存或删除。

需要框架装配关系时，通过关系声明明确表达 `Order.id → OrderItem.orderId`，并遵循既有关系查询契约。同一实体存在多个关联、泛型无法解析或目标不明确时，要求显式配置，不能猜测。

### 外键与关联对象

`Long customerId` 是当前表的外键列，即使携带 `@EntRelation` 仍应保留列映射。`Customer customer` 是关联承载属性，默认不映射当前表列。是否标注关系注解不能单独决定持久化属性资格。

### 临时标量与 JSON 存储

`String customerName` 可能是存储快照，也可能是临时展示值，类型推断无法区分；后者需要显式非持久化配置。

Map、集合或值对象需要整体存入 JSON 列时，必须明确存储映射与转换能力。`EntFieldKind.JSON_DOC` 表达业务种类，不能单独作为对象持久化开关；也不应为了描述关联列表而强制把它标成 JSON 数据库列。

显式标量排除使用现有三态枚举，与 DDL 的 `persisted` 命名一致：

```java
@EntField(value = "客户名称", persisted = OptionalBoolean.FALSE)
private String customerName;
```

`persisted` 默认 `OptionalBoolean.UNSET`，按类型推断；`TRUE` 明确要求单列持久化并验证类型；`FALSE` 明确排除。框架不提供 `exist` 或 `persistent` 参数。

复杂对象的 JSON／自定义转换器 API 尚未开放；当前将它们声明为 `persisted = TRUE` 会在解析注册阶段报错。DDL 原生 `@EntDdlField(persisted = ...)` 可覆盖本模块的默认意图；与公共显式值冲突时，Meta DDL Adapter 按既有优先级选取原生值并保留诊断，业务方应避免相互矛盾的声明。

Meta 校验索引引用的业务属性是否存在；DDL Adapter 在字段与索引的原生覆盖完成后，校验普通索引是否引用最终有效列。原生排除的字段不能用于普通列索引。

## 统一识别与模块职责

`EntityProperties` 统一发现实例属性，`EntityProperty` 保存类型、集合元素类型和三态意图并裁定列资格。Meta Descriptor 保留所有业务属性，通过 `persisted()`、`elementType()` 及来源映射输出结果；复杂属性默认推断为 `EntFieldKind.STRUCTURED`。无法解析的通配符、类型变量及嵌套泛型元素返回 null，不推测实际元素类。

关系描述符分别保留 `relationField()` 和 `sourceField()`，例如 `items` 承载关系，`id` 参与关联；多个关联属性可使用同一个源键。

| 消费者 | 使用边界 |
|---|---|
| Meta | 保留业务属性与关系事实，不将所有属性等同于数据库列 |
| CRUD Runtime Model | 根据统一结果形成列集合和关系集合，校验实际读写能力 |
| DDL | 元数据可保留 `persisted = false` 的属性；SQL 与差异计算仅消费有效列，非列属性不建列、不参与普通列索引 |
| 查询与 JDBC Mapper | 普通列投影、筛选、排序只接受有效列；关系路径使用关系模型 |
| Binder 与普通写入 | 请求出现性、可绑定性、可写性分别判断；非列属性不得进入单表写入值集合 |
| DOC/UI | 可以保留非列属性的名称、说明与结构；展示信息不授予读写权限 |

不新增 Meta 对 JDBC、Spring 或 MyBatis-Plus 的依赖。公共属性分类与显式意图由框架无关层表达，具体存储能力由模块适配并校验；Module-only 与 Meta-first 最终使用一致的列资格语义。

普通列筛选、排序或索引引用非列属性时明确报错。非列属性用作主键、逻辑删除字段或要求物理列的治理字段时同样报错。默认值等配置必须按其所属阶段消费，不能因属性存在便生成数据库操作。

非持久化不等于 JSON 隐藏、只读或允许外部输入。序列化、输入契约和权限仍由各自规则控制；强类型 Handler 可按显式输入契约承接嵌套对象，普通单表 CRUD 不因此接受嵌套写入。

## 当前实现

核验日期：2026-09-27。

| 位置 | 当前事实 | 边界 |
|---|---|---|
| `EntField` | 提供三态 `persisted` | 单列意图不改变序列化或输入权限 |
| `ReflectiveEntMetaParser` | 保留复杂属性，输出列资格与来源、元素类型、`STRUCTURED` 种类 | 名称注解不改变列资格；JSON 种类不启用对象存储 |
| CRUD 原生与 Meta Adapter | 普通列集合使用统一规则 | 非列属性不进入普通单表写入、筛选及排序 |
| DDL 原生与 Meta Adapter | 使用统一类型推断，允许本模块原生意图覆盖 | 原生显式复杂映射也必须校验类型能力 |
| DOC | 保留非列属性描述，结构化属性按对象或数组展示 | 不据此授予输入与持久化权限 |

验收入口为 `EntityPropertyMappingAcceptanceTest`，覆盖跨模块列集合一致、来源与泛型、非列主键／逻辑删除／治理字段拒绝、非列索引拒绝、未支持的显式存储、DOC 描述保留以及 H2 建表与 DAO 读写。原生 DDL Bootstrap/Spring 测试分别覆盖复杂属性默认排除。

## 取舍与实施边界

采用默认推断可以减少主实体挂载关联对象时的重复注解；保留显式配置可以处理临时标量和单列存储的复杂值。代价是类型变化可能影响默认映射，因此必须保留推断来源，并通过模型校验与 DDL 差异审阅识别变化。

不采用“所有实例字段默认都是列”，以避免关联属性反复声明排除；也不采用“所有复杂属性在 Meta 阶段直接丢弃”，以保留关系和业务文档需要的信息。

首期聚焦列资格规则、显式标量排除以及 Meta / CRUD / DDL 一致投影，以订单与明细验证业务手动装配。JSON 转换扩展可以后续实施；没有受支持的映射前，显式请求应报错。

既有关系执行能力继续按原契约使用。本决策不扩张默认自动加载、级联写入、级联删除、多跳查询或循环序列化行为。
