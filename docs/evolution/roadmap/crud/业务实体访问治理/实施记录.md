## 1. G0：唯一主链与真实消费者

下列包名均相对 `com.entloom.crud`，Meta 适配器相对 `com.entloom.meta`。

```text
HTTP / EntCrud*Facade
  → CrudSubjectResolver + CrudInvocationContext
  → Query / Command / Stats / Import / Export Gateway
  → ExecutionPipeline
  → DefaultCrudGovernanceService
      → 主体复制与规范化
      → 服务端属性合并与保留键过滤
      → SpecValidator
      → EntityMetaRegistry → ResourceDescriptor → CrudResourceAction
      → ScenePolicyService
      → CrudPermissionService
      → CrudDataScopeResolver
      → CrudDataScopeContributor + CrudScopeIntersectionService
  → 路由 / Handler / Engine
  → 执行结果审计
```

| 合同或组件 | 当前实现与消费者 | 后续改造边界 |
| --- | --- | --- |
| `CrudGovernanceService` | `core.governance.service.DefaultCrudGovernanceService` 提供五类 Spec 治理入口，`core.execution.ExecutionPipeline` 被各 Gateway 共用 | G3 提取不依赖 Spec 的内核；保留 Gateway 适配，不新增并行授权引擎 |
| Subject Resolver | `core.governance.subject.CrudSubjectResolver`；Facade 显式解析，治理仅在 Spec 无主体时补齐；默认 `FailClosedCrudSubjectResolver` 拒绝 | G1 明确信任来源；现有 Spec 主体属于服务端输入，不可直接作为客户端身份依据 |
| Permission | `core.governance.permission.RuleBasedCrudPermissionService` 无匹配规则即拒绝；Starter 允许替换 `CrudPermissionService` | G2/G3 显式映射业务操作，保留默认拒绝及项目扩展点 |
| DataScope | `core.governance.scope.DefaultCrudDataScopeResolver` 消费已合并服务端属性，默认 org 优先、tenant 次之；缺少范围由治理拒绝 | G3 移除对组织选择即授权的隐含假设；旧 `CrudSubjectNormalizer` 的默认 tenant=`default` 不迁入新主体合同 |
| Contributor | `CrudDataScopeContributor` 经 `CrudScopeIntersectionService` 与已授范围取交集；`ReadVisibilityContributor` 对配置实体的未声明入口拒绝读取 | 保留只收窄原则和实体读取可见性，不把它改成身份权限来源 |
| Scene Policy | `core.governance.policy.DefaultScenePolicyService` 已接入五类治理入口；ACTION、IMPORT、EXPORT 要求策略，ACTION 另校验实体动作声明 | G2 迁移静态入口、portal、动作上限与 capability 映射；不能视为新增能力或替代 Permission |
| DAO 范围 | `core.capability.dao.EntityDaoScopeResolver` 与 `EntityDaoFactory.scoped`；Starter `starter.dao.EntDaoFactoryBean` 每次调用重新解析范围 | G4 消费授权结果并校验资源/动作；当前范围绑定本身不提供操作与字段授权 |

`DefaultCrudGovernanceService` 当前仍有按 Spec 类型展开的编排，不能因为这些入口共用一个实现类，就宣称定制 Service 已获得同义业务操作授权。

| 延后任务 | `core.foundation.taskfile.CrudTaskContextSnapshot` 复制旧主体、范围、属性和审计链；runtime adapter 映射任务合同 | 现有快照不含强类型当前身份，也不等于执行时重新授权。G1/G4 后续落实显式快照与敏感操作重新授权 |

## 3. 静态入口与文档冲突

- 目标文档和旧路线使用了“ResourceMeta 入口校验”的称呼；当前 CRUD 实际资源合同是 `ResourceDescriptor`，字段为实体类型、资源 code、ownerService 和 aliases，未发现对应的通用入口白名单校验。`resourceAction` 从注册表获取描述后构造动作，不执行该旧图中的独立入口校验。
- 这是设计与当前源码的差异，不按既有能力验收，也不补造一个空壳 ResourceMeta。G2 需要明确编译静态资源/操作接入限制；`MetaCrudAdapter` 继续只提供资源元数据，不承担动态授权。
- 必须保留的真实限制：ACTION 的实体声明、ACTION/IMPORT/EXPORT 的 Scene Policy 缺失拒绝、allowedPortals 校验、已声明读取可见性的入口限制、Permission 默认拒绝。
- `ContextAccessEntryAttributeContributor` / `ContextPortalAttributeContributor` 从服务端同步上下文贡献保留属性；默认属性合并器先过滤调用方保留键。新上下文必须保持可信来源边界，不能从业务 payload 恢复这些值。
- `accessEntry` / `portal` 只约束接入面、策略匹配和审计；同一入口不能自动产生业务权限，`common` 也不是身份 code。

## 5. G1.1：上下文合同闭环

- `AccessSubject` 为 final 不可变值对象；以主体 ID 与来源类型共同区分主体。匿名上下文不构造伪账号，服务与设备不默认获得全量权限。
- `BusinessIdentity` 仅要求稳定身份 code 和 ID；项目实现必须是不可变快照。框架不复制任意项目对象，也不声称接口能自动保证实现不可变。
- `VisitorContext` 工厂校验入口、主体和身份坐标；可表达匿名或已认证但尚未选择身份。可信适配器负责认证与身份归属验证，工厂本身不授予可信性。
- `findIdentity` / `requireIdentity` 仅检查唯一当前身份；缺失或类型不匹配拒绝，既不搜索其他身份，也不切换或合并权限。
- `AccessContext.from` 生成匹配身份的只读视图，保留同一个 VisitorContext、实际主体及项目身份。上下文不携带授权结果，不引入 ThreadLocal 或请求属性 Map。
- 目前结构异常使用 API 自身的 `IllegalArgumentException` / `NullPointerException`，当前身份缺失或不匹配使用 `IllegalStateException`。后续接入层需映射为稳定准入拒绝及审计，不能将这些异常当作已完成 HTTP 错误合同。
- G1.1 当时未包含身份注册及 code/类型一致性；现由 G1.2 实现，Core 凭证矩阵由 G1.3 实现。实际可信来源接入、同步身份作用域和任务快照仍未完成，不能标成完整 G1 验收。

## 6. G1.2：身份注册与归属解析闭环

新增实现位于 `com.entloom.crud.core.governance.identity`，不增加 Maven 构件或 Spring/Servlet 依赖：

| 合同 | 责任与边界 |
| --- | --- |
| `BusinessIdentityRegistration<I>` | 绑定项目 code、具体不可变身份快照类型和解析器；拒绝空 code、首尾空格、接口/抽象类型及缺失解析器 |
| `BusinessIdentityResolver<I>` | 接收已认证的实际主体与待验证身份 ID；项目负责核验主体归属、有效成员关系等事实，返回不可变快照；不能只根据输入 ID 构造身份 |
| `BusinessIdentityRegistry` | 构建时拒绝重复 code、同一类型多 code 及空声明，并冻结注册映射；按次调用解析器，检查返回值的 code、精确具体类型、ID 与本次选择一致 |

接入适配器的调用顺序为：完成来源认证取得 `AccessSubject` → `registry.resolve(subject, selectedCode, selectedId)` → 构造 `VisitorContext` → 按需取得 `AccessContext<I>`。认证不能由 Registry 或客户端身份 code 代替。

- 身份 ID 与主体 ID 分离；解析器收到原实际主体，不由身份选择替换发起者。
- 静态注册表只冻结 code/类型/解析器关系，不缓存请求身份或动态归属；再次选择身份必须再次核验事实，已撤销成员关系不能沿用上次解析结果。
- code 和身份 ID 使用精确值，不自动裁剪或大小写转换；注册类型必须与返回快照的运行时类型相同，不接收未注册子类或持久化代理。
- 缺少主体、未知 code、非法坐标、归属解析无结果及结果不一致均抛出 `PermissionDeniedException`；静态注册冲突抛出 `ValidationException`。
- 解析器查询失败直接传播，不降级为匿名或全量身份。异常到接入拒绝、审计与 HTTP 响应的映射留在可信来源适配阶段。
- 框架验证返回结果一致性；实际归属和有效性是项目 SPI 的可信责任，不能宣称框架已自动验证任意数据库成员关系。
- `BusinessIdentityRegistryTest` 以项目商家/教师身份快照验证可扩展性、错误身份选择拒绝、撤销后重新解析和保留项目字段；这些身份仅存在于测试，不写入 Core 生产模型。

G1.2 当时尚未提供 Starter 自动装配、HTTP 接入或 Controller 注入；现由 G1.4 提供声明式 MVC 接入。现有 CRUD 治理链迁移及身份权限映射仍未实现。

## 7. G1.3：Core 认证准入与公共分支隔离

新增合同与编排不依赖 Servlet、Spring 或 CRUD Spec：

| 合同 | 责任与边界 |
| --- | --- |
| `api.access.AuthenticationMode` | REQUIRED、OPTIONAL、ANONYMOUS；服务默认入口使用 REQUIRED，不表示旧 HTTP 接口已经迁移 |
| `api.access.AccessBranch` | PUBLIC 与 AUTHENTICATED，明确后续策略分支；不是资源操作授权结论 |
| `core.governance.admission.CredentialAuthentication` | 不可变来源结果，区分 ABSENT、AUTHENTICATED、INVALID；有效凭证必须保留实际主体，身份选择可缺省但 code/ID 必须成对有效；不存凭证原文 |
| `AccessAuthenticationSource` | 项目按次验证实际凭证并返回来源结果；仅无凭证可返回 ABSENT，无效/过期必须返回 INVALID；来源失败不得伪装成无凭证 |
| `AccessAdmissionService` | 所有模式先调用认证来源，再选分支；主体分支按需调用身份 Registry；公共分支不查询或合并身份选择 |
| `AccessAdmission` | 保留认证模式、有效 VisitorContext、策略分支及单独的实际认证主体审计字段；不缓存请求，不提供数据范围或操作授权 |

### 已验证的完整 Core 凭证矩阵

| 模式 | ABSENT | AUTHENTICATED | INVALID（含过期） |
| --- | --- | --- | --- |
| REQUIRED | 拒绝 | 主体分支；有身份选择时重新验证归属 | 拒绝 |
| OPTIONAL | 公共分支 | 主体分支；有身份选择时重新验证归属 | 拒绝 |
| ANONYMOUS | 公共分支 | 仍认证凭证，只走公共分支；实际主体单独用于审计 | 拒绝 |

- ANONYMOUS 的有效 `VisitorContext` 不含主体或当前身份，实际主体仅从 `AccessAdmission.getAuthenticatedSubject()` 供审计使用。不能将审计主体重新合入公共分支，否则会破坏匿名模式语义。
- ANONYMOUS 不验证个性化身份选择的归属，也不保留该选择为已验证身份；有效凭证中的未知身份选择不改变公共权限。公共操作仍需显式策略授权，不因准入成功而自动可访问。
- REQUIRED/OPTIONAL 的身份选择经 `BusinessIdentityRegistry` 按次校验；未知 code、归属不符或错误解析结果立即拒绝。
- 有效主体尚无当前业务身份时仍可完成认证准入，但 `requireIdentity` 拒绝，后续接口或策略另行要求身份；不会给服务或设备主体创建默认身份。
- 来源返回 null、凭证无效或 REQUIRED 缺少凭证，使用现有 `PermissionDeniedException` 拒绝。认证来源抛出的错误保持传播，不降级为匿名。认证专用 HTTP 状态与审计映射留在接入阶段。
- 接入层必须在调用 Controller 之前独立执行准入，不能以方法是否声明上下文参数决定是否调用；G1.3 当时仅建立 Core 服务及测试，现由 G1.4 实现声明接口的 HTTP 接入路径。
- 工厂与 SPI 无法替项目验证凭证算法或确认认证结果的真实性；本轮验证的是可信 SPI 结果上的编排矩阵，不宣称已经完成真实 Token、会话、设备签名验证或防伪 body 的 HTTP 验收。

## 8. G1.4：声明式 MVC 准入与上下文注入

实现落在现有 CRUD Annotations / Starter，不新增 Maven 构件，不依赖业务实体或新授权引擎。

```text
项目已有登录或来源认证机制
  → CrudHttpAuthenticationSource（真实凭证验证及服务端入口元数据）
  → AccessAuthenticationFilter（失败拒绝、绑定当前分派的类型化可信状态）
  → 实际 Handler 的 @EntAccess 声明
  → AccessAdmissionService + BusinessIdentityRegistry
  → 接口模式与显式身份要求校验
  → VisitorContext / AccessContext<I> 参数注入
  → Controller / Service（仍需业务操作授权）
  → Filter finally 清理请求状态
```

| 接入能力 | 已实施合同与边界 |
| --- | --- |
| `@EntAccess` | 类/方法上的认证模式与当前身份要求；默认 REQUIRED；方法声明整体覆盖类声明。它不是资源操作或数据范围授权 |
| `CrudHttpAuthenticationSource` | 项目实现实际凭证认证，返回 `HttpAccessAuthentication`；可信入口、requestId/traceId 由适配器提供，框架没有从 body/Header 猜主体的默认实现 |
| `CrudAccessWebAutoConfiguration` | 独立于内置 CRUD Controller 开关装配注册表、Core 准入与 MVC 接入；身份声明 Bean 统一收集，已有 Registry/Service 可覆盖；没有可信来源时声明接口拒绝，而不是自动匿名 |
| `AccessAuthenticationFilter` | 仅在项目提供 HTTP Source Bean 时自动注册，默认晚序执行以便对接已有认证链；注册所有 Servlet 分派类型，异步/错误再分派不主动跳过认证；每次覆盖预存状态并 finally 清理 |
| `AccessAdmissionInterceptor` | 按实际 Handler 的声明执行认证模式及身份准入，不用路径匹配产生权限；无上下文参数的接口同样检查身份。仅从 Filter 写入的类型化状态读取认证结果 |
| `AccessContextArgumentResolver` | 只注入已准入、绑定当前 Handler 的上下文；缺少声明或准入结果拒绝，不回退到业务 payload 或普通属性 Map |
| HTTP 错误 | 复用既有 `CrudHttpErrorMapper`、`CrudResponseBuilder`：凭证/身份拒绝为 403，声明/参数结构错误为 400，认证来源故障为通用 500；来源异常不将原消息或凭证细节返回客户端 |

### 接入约定与安全边界

- HTTP Source Bean 是项目明确接入认证能力的开关。提供后，Filter 对应用内请求统一验证已有凭证，因此未声明接口的无效凭证也拒绝；无凭证的普通旧接口保持原行为。
- 未提供 Source 时不注册认证 Filter；`@EntAccess` 声明接口即使为 ANONYMOUS 也拒绝，因为不能证明请求确实无凭证。普通未声明旧接口仍走原有链，不宣称已全量迁移。
- 准入要求由注解独立表达，不从参数推导权限。固定身份参数必须写成 `AccessContext<项目身份类>`，且与 `@EntAccess(identity = 项目身份类.class)` 相同；删除参数不会删除注解的身份要求。
- `VisitorContext` / `AccessContext<I>` 参数不声明请求绑定注解；`@RequestBody` 等绑定注解、raw/wildcard/未确定泛型或与声明不一致的固定身份参数均拒绝，防止被 MVC 的普通请求解析器接管。
- 示例接入：`@EntAccess(identity = MerchantIdentity.class)` 的方法可接收无绑定注解的 `AccessContext<MerchantIdentity>`；业务 payload 仍单独使用普通 DTO 参数。该示例只说明准入及注入，不表示获得订单等资源的操作权限。
- 请求属性仅保存框架 Filter 创建的内部类型化状态，普通属性 Map 不成为身份来源。Filter 主动覆盖同名预存值，准入结果还绑定实际 Handler 方法，结束后清理；没有新增 ThreadLocal 或单例当前身份字段。
- ANONYMOUS 注入的有效上下文仍不含实际主体或当前身份。其认证主体留在内部 `AccessAdmission` 的审计字段，未自动合入公共分支。
- 已验证同步 HTTP 正常/异常清理和两类身份并发请求隔离；这不等于异步业务任务已重新授权。敏感延后任务、显式快照与非 Servlet 的 Core 同步作用域仍留待 G1 后续阶段。
- 项目必须正确实现真实会话、Token、设备认证及身份归属 SPI。本轮测试使用受控认证夹具，不能宣称已经集成真实认证后端或设备签名；复杂认证链需项目确认 Filter 顺序。
- 未迁移旧 CRUD Controller / Facade / Gateway 到新合同，未加入业务操作授权与 DAO 结果消费。HTTP 认证拒绝审计的统一记录、任务授权及事务结果审计仍待后续收敛；当前错误包络不是完整审计证据。

## 9. 验收矩阵与回归基线

### G1.5：Core 同步作用域与显式任务快照

- `AccessContextScope.withAdmission` 仅在当前线程绑定 Core 准入结果；嵌套调用与异常退出都恢复原值，空闲线程移除 ThreadLocal。可直接从当前结果读取有效 `VisitorContext`，公共分支不会被审计主体替代。

## 55. G4.31：JDBC 逐目标批量 UPDATE 全量原子与商家改价演示 {#55-g431-jdbc-逐目标批量-update-全量原子与商家改价演示}

> 状态：Completed；真实 HTTP/H2 双端测试 25 项、完整示例 H2 55 项、脚本单测 8 项通过，Java 打包成功；JDK 21.0.12.1 真实 MySQL 整轮验收 exit 0，G4.32 完成。
