# 商家批量改价演示

> 状态：Current；2026-10-16 商品维护统一使用通用 CRUD，专用 Controller、Service、DTO 和改价错误枚举已删除。
> 实现位置：[mini-commerce merchant](https://github.com/ent-loom/ent-loom/tree/main/examples/mini-commerce-spring-boot/src/main/java/com/example/minicommerce/merchant/)。
> 框架执行合同：[实体 DAO](../../architecture/components/crud/实体DAO.md)、[批量 CRUD 调用指南](批量CRUD调用指南.md)。

商品名称、销售价和启用状态由商家维护。读取和批量局部更新均复用框架入口；示例仅声明实体、业务访问策略及字段约束。框架负责可信准入、逐目标授权、归属范围、字段权限、版本、整批事务和审计。

## 实体与约束

[MerchantProduct](../../../examples/mini-commerce-spring-boot/src/main/java/com/example/minicommerce/merchant/entity/MerchantProduct.java) 在实体文件中选择 `maintainable` 策略，默认资源码为 `merchantProduct`，数据库表为 `merchant_product`。

- `merchantId` 是商家归属字段，普通更新不能修改。
- `version` 是每项预期版本，更新成功后由框架递增，不能作为普通字段赋值。
- `name` 和 `active` 不允许显式清空；未提交时仍保持原值。
- `price` 上声明 `@NotNull`、`@DecimalMin` 和 `@Digits`：价格须大于 0，最多 14 位整数和 6 位小数。
- 框架通过应用的 Spring `SmartValidator` 校验显式提交的实体字段。未提交字段保持原值，不因实体非空约束被当作必填；显式 `null` 须通过对应约束。

本示例已有 Bean Validation 运行时。框架无须依赖 Jakarta Validation API，Core 通过 `EntityWriteValidator` 接口支持应用替换校验实现。

## 访问配置

[application.yml](../../../examples/mini-commerce-spring-boot/src/main/resources/application.yml) 声明商家身份、实体策略及字段权限，相关部分如下：

```yaml
ent:
  loom:
    crud:
      access:
        identities:
          merchant:
            id-type: LONG
        relations:
          merchant:
            field: merchantId
        policies:
          maintainable:
            actions: [view, create, update, delete]
            access:
              merchant:
                actions: [view, create, update, delete]
                scope: merchant
```

商品实体就近声明写入授权，使用 ALL 沿用元数据写入保护：

```yaml
# ent/entities/merchantProduct.yml
crud:
  access:
    policy: maintainable
    actions:
      add: [batch-update]
    merchant:
      actions:
        add: [batch-update]
      fields:
        WRITE: {mode: ALL}
```

`update` 仅授权单条 `UPDATE`；`batch-update` 独立授权 `UPDATE_BATCH`，每个目标分别校验身份、范围、字段与版本，整批成功或回滚。

`maintainable` 提供所属商家的增删改查缺省，批量更新由实体显式增加。当前接入单条 CREATE/UPDATE/DELETE 与批量 UPDATE；未接入动作启动失败。

服务端演示账号在 [demo.yml](../../../examples/mini-commerce-spring-boot/src/main/resources/demo.yml) 中配置：

| Token | 商家 ID |
| --- | ---: |
| `demo-merchant-a` | 1001 |
| `demo-merchant-b` | 2001 |

认证来源为 `CrudHttpAuthenticationSource`。框架按实际内置 Handler 和已暴露的策略实体执行 REQUIRED 准入；身份来自服务端账号绑定，不能通过请求体或 Header 切换。

## 初始化与读取

按示例 [README](https://github.com/ent-loom/ent-loom/blob/main/examples/mini-commerce-spring-boot/README.md) 安装当前工作区构件并启动应用，执行 [merchant-demo.sql](../../../examples/mini-commerce-spring-boot/scripts/merchant-demo.sql) 初始化数据。脚本只补缺失记录，不重置已有价格与版本。

| 商品 ID | 商家 ID | 初始价格 | 初始版本 |
| --- | ---: | ---: | ---: |
| 101 | 1001 | 10.00 | 0 |
| 102 | 1001 | 20.00 | 0 |
| 201 | 2001 | 30.00 | 0 |

```sh
curl -X POST http://localhost:8082/api/ent-crud/merchantProduct/list \
  -H 'Authorization: Bearer demo-merchant-a' \
  -H 'Content-Type: application/json' \
  -d '{"options":{"limit":100}}'
```

商家 A 只能看到 101/102，商家 B 只能看到 201，记录在 `data.items` 中。后续更新的版本使用实际查询返回值。

## 通用批量局部更新

```sh
curl -X POST http://localhost:8082/api/ent-crud/merchantProduct/updateBatch \
  -H 'Authorization: Bearer demo-merchant-a' \
  -H 'Content-Type: application/json' \
  -d '{"payload":{"items":[{"id":101,"price":11.50,"version":0},{"id":102,"price":22.00,"version":0}]}}'
```

成功结果的 `data` 为：

```json
{
  "rows": 2,
  "items": [
    {"operation": "UPDATE", "id": 101, "rows": 1},
    {"operation": "UPDATE", "id": 102, "rows": 1}
  ]
}
```

每项可以提交不同字段，例如一项修改 `name`，另一项修改 `active`。省略的字段保持原值；显式 `null` 表示清空允许为空的字段；本例商品名称、价格和启用状态均不允许清空。

执行链为 `通用 HTTP → CommandGateway UPDATE_BATCH → AuthorizedBatchUpdateExecutor → 授权 DAO 批量写入`。全部主键、Patch、字段和版本准备完成后，底层开启整批事务；SQL 关键结构如下，由框架生成：

```sql
UPDATE merchant_product
SET price = ?, version = version + 1
WHERE merchant_id = ? AND id = ? AND version = ?
```

首期只接受普通根实体、每批 1～500 项、不重复的主键。必须由框架拥有最终提交边界，不接受外层事务、全局版本、全局目标过滤、场景、试运行或幂等键。无版本字段的实体不要求版本；本例有版本字段，因此每项必须携带当前版本。

## 失败与审计

| 情况 | 结果 |
| --- | --- |
| 空批次、重复目标、缺失版本、非法金额或类型 | 400，整批不写入 |
| 缺失凭证、无效凭证或身份无权限 | 403 |
| 未授权字段、归属变更或不支持的命令形状 | 在 SQL 前拒绝 |
| 商品不存在、跨商家或版本已过期 | `409 WRITE_CONFLICT`，整批回滚 |
| 任一 SQL 或提交失败 | 整批失败，不返回部分成功 |

写入未命中不区分不存在、跨范围或版本冲突，不额外探测目标存在性。错误码由框架直接映射，无需业务异常转换。

成功返回表示最终 commit 已完成，之后才逐目标记录成功审计。写入失败的审计故障不覆盖原异常；提交后审计故障只记录日志，不把已提交数据变为可重试失败。当前没有持久 outbox，不保证进程故障后的审计补投，也不保证数据与审计持久化原子一致。客户端需重新查询以获取新版本；网络结果不明时先读取本人商品，避免直接重复提交。

完整请求顺序见 [merchant.http](../../../examples/mini-commerce-spring-boot/requests/merchant.http)。自动测试覆盖商品更新、实体约束、归属隔离、版本及回滚；真实 MySQL 验收需使用示例的独立验收环境。
