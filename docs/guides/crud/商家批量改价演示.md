# 商家批量改价演示

> 状态：Current；2026-10-12 声明迁入主 YAML，示例 H2 55 项、脚本单测 8 项通过。G4.31/G4.32 的真实 MySQL 验收保留为历史证据，不代表本轮已重跑 MySQL。
> 实现位置：[mini-commerce merchant](../../../examples/mini-commerce-spring-boot/src/main/java/com/example/minicommerce/merchant/)。
> 框架执行合同：[实体 DAO](../../architecture/components/crud/实体DAO.md)；验证证据：[G4.31 实施记录](../../evolution/roadmap/crud/业务实体访问治理/实施记录.md#55-g431-jdbc-逐目标批量-update-全量原子与商家改价演示)。

本示例把“商家只读本人报价、只修改价格、混入越界或过期目标时整批不生效”接入同一业务授权链。业务负责账号归属、操作策略、DTO 和错误提示；框架负责逐目标授权、范围与字段约束、版本条件、事务及最终审计。

## 1. 实体与命名

[MerchantProduct](../../../examples/mini-commerce-spring-boot/src/main/java/com/example/minicommerce/merchant/entity/MerchantProduct.java) 使用以下声明：

```java
@EntEntity("商家商品")
public class MerchantProduct implements MerchantData {
    // 省略 @EntField 元数据与 getter/setter；完整声明见源文件。
    private Long id;
    private Long merchantId;
    private String name;
    private BigDecimal price;
    private Boolean active;
    private Long version;
}
```

| 名称 | 用途 |
| --- | --- |
| `MerchantProduct` | Java 实体类型 |
| `merchantProduct` | 默认资源码，业务操作和授权资源校验使用此名称 |
| `merchant_product` | 默认数据库表名，只用于存储 |
| `merchant-data` | 示例静态策略模板 ID |

`productId` 声明只读；`merchantId` 命中全局 `access.relations.merchant.field` 的缺省归属推导，自动成为范围字段，禁止普通 Patch 改归属。`version` 是预期版本输入和框架自增字段，不能作为普通变更字段写入。主 YAML 的通用 HTTP 白名单不包含该实体；定制商家接口仍须显式准入与授权。

## 2. 服务端账号配置与准入

在示例 [application.yml](../../../examples/mini-commerce-spring-boot/src/main/resources/application.yml) 配置演示账号：

```yaml
ent:
  loom:
    crud:
      access:
        identities:
          merchant:
            id-field: merchantId
            id-type: LONG
      example:
        enabled: true
        default-access-entry: consumer
        routes:
          "[/api/merchant/**]": merchant
        accounts:
          - token: demo-merchant-a
            subject-id: merchant-user-a
            merchantId: 1001
          - token: demo-merchant-b
            subject-id: merchant-user-b
            merchantId: 2001
```

主 YAML 的 `access.identities.merchant` 声明 `id-field: merchantId` 和 `id-type: LONG`。Starter 按身份码注册统一不可变快照，`ConfiguredExampleAccounts` 绑定静态账号并提供 `CrudHttpAuthenticationSource`；Controller 使用 `@EntAccess(identity = "merchant")`，无需商家身份类或认证配置类。

启动时校验身份定义、ID 转换、入口引用、唯一令牌和唯一主体；请求按 `Authorization: Bearer <token>` 精确匹配账号，并在准入时再次核验 `HUMAN` 主体与商家归属。缺失或无效凭证返回 403，客户令牌不能进入商家端。入口由服务端路由映射决定，与身份码分别配置。

商家 ID 来自服务端账号表，不接收请求体指定的身份或归属。两枚固定令牌仅用于本地演示；正式接入替换认证来源和身份归属解析器。

示例通用 HTTP 仅开放 `ent.loom.crud.access.entities` 清单内的实体。订单明细 `orderItem` 未进入清单，不开放通用接口；`order_item` 是表名，不能用于实体接口配置。

## 3. 主 YAML 策略与关系范围

[application.yml](../../../examples/mini-commerce-spring-boot/src/main/resources/application.yml) 的 `ent.loom.crud.access` 直接声明：

```yaml
policies:
  merchant-data:
    merchant:
      actions: [view, update]
relations:
  merchant:
    field: merchantId
field-plans:
  merchantProduct:
    merchant:
      WRITE:
        mode: INCLUDE
        fields: [name, price, active]
```

`merchant-data` 声明商家读取、维护本人数据，实体通过项目接口 [MerchantData](../../../examples/mini-commerce-spring-boot/src/main/java/com/example/minicommerce/merchant/model/MerchantData.java) 选择，无需再登记 `policy-bindings`；接口要求 `getMerchantId()`，由 Lombok 生成实现。`RETURN/FILTER` 采用框架缺省，`field-plans.merchantProduct.merchant.WRITE` 仅约束商家的可写字段，当前改价接口 DTO 只接收价格。`scope` 缺省为已登记的身份同名关系；`identity-field` 缺省为 `merchantId`。框架从可信 `merchant` 身份快照的声明 ID 属性读取关系事实，并将它与动态业务范围、实体字段上限及调用方筛选取交集。标准动作缺省推导 `view` 的普通查询映射及 `update` 的单条 UPDATE 映射；静态策略、接口绑定和动作目录在启动时汇入同一 Core 编译器；不再需要 `MerchantAccessConfiguration` 或手写简单关系判定器。

每个写入目标分别授权、分别消费自己的范围与 `WRITE`。知道其他商家的报价 ID 不会获得写权限；SQL 仍必须包含当前商家的 `merchantId` 条件。项目需要动态权限时可提供 `BusinessPermissionEvaluator`，仅进一步收窄或拒绝。当前 YAML 不表达复杂关系解析器、场景 ACTION、自由 SQL 或权限继承，这些继续通过 Java 显式接入。

## 4. Controller 与 Service

[MerchantPricingController](../../../examples/mini-commerce-spring-boot/src/main/java/com/example/minicommerce/merchant/web/MerchantPricingController.java) 的类级准入固定为：

```java
@RequestMapping("/api/merchant/products")
@EntAccess(identity = "merchant",
    accessEntries = "merchant", subjectTypes = AccessSubjectType.HUMAN)
```

方法接收框架注入的 `AccessContext`，只传其 `VisitorContext` 给 Service。

| 接口 | 执行与返回 |
| --- | --- |
| `GET /api/merchant/products` | `AuthorizedQueryExecutor.list` 查询本人报价，最多 100 条，`data` 为受返回字段能力约束的记录 |
| `POST /api/merchant/products/prices` | 接收 `{items:[{id,price,version}]}`，1～100 项；成功 `data` 为输入顺序的报价 ID 列表 |

[ChangePricesCommand](../../../examples/mini-commerce-spring-boot/src/main/java/com/example/minicommerce/merchant/dto/ChangePricesCommand.java) 位于 `merchant.dto`，内部定义 `PriceChange`，由 Controller 与 Service 共用。DTO 仅暴露 `id`、`price`、`version`：ID 必须为正整数，预期版本非负且必填，价格必须大于 0，最多 14 位整数、6 位小数。空项、空集合、超过 100 项或非法载荷以 400 拒绝；重复目标由 Core 批次前门拒绝。接口不接受商家范围配置。

[MerchantPricingService](../../../examples/mini-commerce-spring-boot/src/main/java/com/example/minicommerce/merchant/service/MerchantPricingService.java) 注入 `AuthorizedQueryExecutor`、`EntityDaoAuthorizationProvider` 和 `EntityMetaRegistry`。框架当前不提供默认 `CommandPayloadBinder` Bean，Service 用内部 final 字段直接复用 `DefaultCommandPayloadBinder` 实现，`PriceChange` 来自 `ChangePricesCommand.PriceChange`；关键调用为：

```java
private final CommandPayloadBinder patches = new DefaultCommandPayloadBinder();

public List<CrudRecord> list(VisitorContext visitor) {
    return queries.list(visitor, QuerySpec.<CrudRecord>builder().rootType(MerchantProduct.class)
        .resultType(CrudRecord.class).op(QueryOperation.LIST).limit(100).build());
}

// 不包裹外层事务；批量 DAO 必须拥有最终提交边界。
public List<Long> changePrices(VisitorContext visitor, List<PriceChange> changes) {
    var type = EntityType.of(MerchantProduct.class, Long.class);
    var writer = daos.openBatchWrite(type, visitor, new BusinessOperation("merchantProduct", "update"),
        changes.stream().map(change -> change.id().toString()).toList());
    var meta = entities.getEntityMeta(MerchantProduct.class);
    var items = changes.stream().map(change -> EntityDaoBatchWriteRequest.Item.update(
        change.id().toString(), change.id(), patches.bindUpdatePatch(
            Map.of("id", change.id(), "price", change.price(), "version", change.version()),
            MerchantProduct.class, meta))).toList();
    writer.execute(EntityDaoBatchWriteRequest.of(writer.getAuthorization(), items));
    return changes.stream().map(PriceChange::id).toList();
}
```

框架先 prepare 全部目标，校验主键、Patch 版本快照和字段能力，冻结 SQL 参数后开启独立事务。以报价表为例，每目标 SQL 的关键结构为（仅示意，不由业务拼接）：

```sql
UPDATE merchant_product
SET price = ?, version = version + 1
WHERE merchant_id = ? AND id = ? AND version = ?
```

任一目标影响行数不是 1 或 SQL/事务失败，整批回滚并抛原异常，不返回部分成功，也不回填 Patch 版本。成功返回表示最终 commit 已完成；获得新版本需重新 GET。已有外层事务时拒绝执行，不能把尚未提交的事务回调结果视为成功。

## 5. 请求与失败语义

使用当前工作区构件的安装与应用启动步骤见示例 [README](../../../examples/mini-commerce-spring-boot/README.md)。应用启动并自动建表后，在 `examples/mini-commerce-spring-boot` 目录另开终端执行已提供的 [merchant-demo.sql](../../../examples/mini-commerce-spring-boot/scripts/merchant-demo.sql)：

```sh
docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_PASSWORD" mysql -u"$MYSQL_USER" "$MYSQL_DATABASE"' < scripts/merchant-demo.sql
```

脚本用 `INSERT IGNORE` 只补缺失记录，不重置已有报价的价格或版本。商品主数据使用 900010/900020；商家报价 fixture 为：

| 报价 ID | 商品 ID | 商家 ID | 初始价格 | 初始版本 |
| --- | --- | --- | --- | --- |
| 101 | 900010 | 1001 | 10.00 | 0 |
| 102 | 900020 | 1001 | 20.00 | 0 |
| 201 | 900010 | 2001 | 30.00 | 0 |

按 [merchant.http](../../../examples/mini-commerce-spring-boot/requests/merchant.http) 顺序执行即可观察读取隔离、改价成功、跨商家与旧版本全批回滚、403 准入和通用路由 404。先读取本人报价：

```sh
curl -H 'Authorization: Bearer demo-merchant-a' \
  http://localhost:8082/api/merchant/products
```

首次初始化后，商家 A 返回 101/102，商家 B 返回 201。以下以 A 的两条报价改价，version 使用 GET 返回值；新插入的 fixture 初始为 0：

```sh
curl -X POST http://localhost:8082/api/merchant/products/prices \
  -H 'Authorization: Bearer demo-merchant-a' \
  -H 'Content-Type: application/json' \
  --data '{"items":[{"id":101,"price":11.50,"version":0},{"id":102,"price":22.00,"version":0}]}'
```

首次成功返回 `data: [101,102]`，再 GET 可见价格为 11.50/22.00、版本均为 1。随后按请求文件混入 201 或对 102 使用旧版本 0，均返回 409 且 101/102 保持成功提交后的价格和版本。`demo-merchant-b` 只读/写商家 2001 的报价；报价创建通过本地初始化 SQL 完成。

Controller 将 `EntityDaoWriteMissException` 统一映射为 `409 PRICE_UPDATE_REJECTED`，提示“报价不可更新或版本已变化，整批未生效；请重新读取本人报价”。不区分不存在、跨商家、版本冲突，也不追加存在性探测查询。其他框架异常复用 `CrudHttpErrorMapper`；缺失或无效凭证为 403。

`MerchantProduct` 的通用 HTTP 写入返回 `404 ENTITY_NOT_EXPOSED`，表示实体禁止通用路由暴露，定制商家入口是该演示的受治理访问路径。

逐目标成功审计只在 commit 后记录；写入失败时审计故障不覆盖原异常。commit 后审计故障记日志并继续其余目标，不把已经提交的改价变为可重试失败。当前没有持久 outbox，不保证进程故障后的审计补投，也不保证数据与审计持久化原子一致。

实体 DOC 合同来自 Meta 实体与字段；报价定制接口的路由、DTO、准入和错误语义来自 Controller、本指南与 `merchant.http`。通用 HTTP 白名单仅控制 CRUD 路由，不隐藏实体 DOC；演示 DOC 仍使用 `local-developer` 暴露配置，商家令牌不自动获得文档权限。

当前 JDBC 入口只支持批量 UPDATE。批量 DELETE/INSERT、部分成功、归属变更、持久审计和统一框架 write miss 映射属于后续需求扩展；既有验证证据统一维护在 G4.31 实施记录，G4.32 配置迁移后的结果维护在 G4.32 实施记录。
