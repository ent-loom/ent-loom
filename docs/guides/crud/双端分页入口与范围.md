# 双端分页入口与范围

> 状态：Current（G4.32 已完成）；真实 HTTP/H2 双端 25 项、完整示例 H2 55 项、脚本单测 8 项通过，Java 打包成功；JDK 21.0.12.1 真实 MySQL 整轮验收 exit 0。
> 示例：[Mini Commerce](../示例工程.md)；验证证据：[G4.32 实施记录](../../evolution/roadmap/crud/业务实体访问治理/实施记录.md#56-g432-同一商家子订单的双端分页入口与范围)。

同一个分页业务可以开放两个入口：用户只看自己的商家子订单，商家只看自己承接的子订单。两端共用一张表、一个 `view` 业务操作和同一个 `AuthorizedQueryExecutor.page`；可信身份决定授权范围，请求中的对侧 ID 进一步收窄查询。

本轮用种子数据准备商家子订单，原下单流程尚未自动拆单；演示范围限于双端分页。

## 1. 实体与操作

[MerchantOrder](../../../examples/mini-commerce-spring-boot/src/main/java/com/example/minicommerce/order/entity/MerchantOrder.java) 声明 `@EntEntity("商家销售订单")` 并实现项目分类接口 [OrderEntries](../../../examples/mini-commerce-spring-boot/src/main/java/com/example/minicommerce/order/model/OrderEntries.java)，接口通过 `@EntCrudPolicy(template = "order-entries")` 选择双端读取策略，并要求 `getCustomerId()` 与 `getMerchantId()`。主 YAML 的全局 `relations` 按已有字段缺省推导两个归属字段。两项范围字段表示可用于归属约束；每次授权具体使用哪一项由当前身份分支决定。

| 名称 | 用途 |
| --- | --- |
| `merchant_order` | 两端共用数据库表 |
| `merchantOrder` | 实体资源码 |
| `merchantOrder/view` | 两端共用业务操作 |
| `order-entries` | 静态策略模板 ID，含 `customer` 与 `merchant` 两个身份分支 |
| `ent.loom.crud.access` | 主 YAML 的策略、操作目录和绑定来源 |

[application.yml](../../../examples/mini-commerce-spring-boot/src/main/resources/application.yml) 的 `access.policies.order-entries` 声明两个 `view` 身份分支，实体通过 `OrderEntries` 选择策略，无需额外 YAML 绑定；省略 `operations` 后由 `view` 推导普通查询映射，双端定制入口实际执行 PAGE。`relations.customer/merchant` 登记归属关系，缺省身份属性为 `customerId/merchantId`。框架在启动时编译成同一 Core 策略；已删除 `OrderAccessConfiguration`。通用 HTTP 白名单不包含该实体，定制接口显式接入准入与授权链。

## 2. 可信身份与两个入口

[application.yml](../../../examples/mini-commerce-spring-boot/src/main/resources/application.yml) 的演示账号如下：

| 配置 | Bearer 令牌 | 主体 | 当前身份 ID |
| --- | --- | --- | --- |
| `example.accounts[].customerId` | `demo-customer-a` | `customer-user-a` | 客户 301 |
| `example.accounts[].customerId` | `demo-customer-b` | `customer-user-b` | 客户 302 |
| `example.accounts[].merchantId` | `demo-merchant-a` | `merchant-user-a` | 商家 1001 |
| `example.accounts[].merchantId` | `demo-merchant-b` | `merchant-user-b` | 商家 2001 |

主 YAML 的 `access.identities.customer/merchant` 分别声明 `customerId/merchantId` 和 `LONG` 类型，Starter 按业务身份码注册统一不可变快照。`example.accounts` 精确匹配 `Authorization: Bearer <token>`，绑定 `HUMAN` 主体与身份 ID；准入时再次核验归属。入口用 `@EntAccess(identity = "customer")` 或 `"merchant"`，不再依赖身份类或泛型上下文。令牌和主体必须唯一，可信入口由 `example.default-access-entry` 与 `example.routes` 按服务端路由确定。

| 入口 | `@EntAccess` | 授权 scope | 可选额外 filter |
| --- | --- | --- | --- |
| `POST /api/consumer/orders/page` | `customer`、`HUMAN`、`consumer` | `customerId = 当前客户` | `merchantId = 请求值` |
| `POST /api/merchant/orders/page` | `merchant`、`HUMAN`、`merchant` | `merchantId = 当前商家` | `customerId = 请求值` |

两个 Controller 从注入的 `AccessContext` 取得可信 `VisitorContext`。请求体及 `X-Customer-Id`、`X-Merchant-Id`、`X-Access-Entry` 等客户端 Header 不能切换当前身份或入口；对侧令牌跨端访问返回 403。正式接入时替换演示认证来源与身份归属解析器。

主 YAML 省略双端只读字段方案：`RETURN` 缺省返回全部普通字段（包括状态和创建时间，不展开关系），`FILTER` 缺省允许其中可筛选的字段。入口 DTO 仅接收用户端的 `merchantId` 或商家端的 `customerId`；未指定排序时框架按主键稳定排序，调用方主动排序仍须 `SORT` 授权。框架读取当前可信身份的简单关系并生成范围；无需手写 `BusinessPermissionEvaluator` 或关系解析 Bean。[商家报价改价](商家批量改价演示.md)复用同一声明式编译和授权链。

## 3. DTO 与共用分页执行

[OrderPageQueries](../../../examples/mini-commerce-spring-boot/src/main/java/com/example/minicommerce/order/dto/OrderPageQueries.java) 分为 `Consumer`、`Merchant`：

| 请求字段 | 用户端 | 商家端 |
| --- | --- | --- |
| `pageNumber` | 默认 1，最小 1 | 默认 1，最小 1 |
| `pageSize` | 默认 20，范围 1～100 | 默认 20，范围 1～100 |
| `merchantId` | 可选，正整数 | 当前归属字段，传入返回 400 |
| `customerId` | 当前归属字段，传入返回 400 | 可选，正整数 |

严格 DTO 不接受当前归属字段、通用 filters、排序或计数模式。用户端请求体传入 `customerId`、商家端传入 `merchantId` 均返回 `400 VALIDATION_ERROR`；伪造 Header 不改变查询范围。[OrderPageService](../../../examples/mini-commerce-spring-boot/src/main/java/com/example/minicommerce/order/service/OrderPageService.java) 的 `consumerPage()`、`merchantPage()` 共用以下私有执行方法：

```java
private PageResult<CrudRecord> page(VisitorContext visitor, int number, int size, String field, Long value) {
    var page = new PageQuery(number, size,
        List.of(new QuerySort("id", SortDirection.ASC)), CountMode.ALWAYS);
    var filters = value == null ? List.<QueryFilter>of()
        : List.of(new QueryFilter(field, FilterOperator.EQ, value));
    return queries.page(visitor, QuerySpec.<CrudRecord>builder()
        .rootType(MerchantOrder.class).resultType(CrudRecord.class)
        .op(QueryOperation.PAGE).pageQuery(page).filters(filters).build());
}
```

框架把授权 scope 与请求 filter 取 AND，分别用于数据 SQL 和 count SQL。`CountMode.ALWAYS` 每次计算总数，排序固定 `id ASC`；业务 Service 只组装分页和额外筛选。本轮复用既有根实体 PAGE 执行能力，没有新增框架公共 API 或 Core/JDBC 代码。

以客户 301 筛选商家 1001 为例，SQL 关键结构如下（框架参数化生成，省略别名）：

```sql
SELECT id, order_id, customer_id, merchant_id, total_amount
FROM merchant_order
WHERE customer_id = ? AND merchant_id = ?
ORDER BY id ASC LIMIT ? OFFSET ?;

SELECT COUNT(*) FROM merchant_order
WHERE customer_id = ? AND merchant_id = ?;
```

两条 SQL 的范围与筛选参数均为 `301, 1001`；商家 1001 筛选客户 301 时，授权条件为 `merchant_id = ?`，额外筛选为 `customer_id = ?`。`total` 是完整授权范围与额外筛选的交集数量，不是当前页条数。

## 4. 种子数据与顺序演示

按示例 [README](../../../examples/mini-commerce-spring-boot/README.md) 安装当前工作区构件并启动应用。建表后在示例目录执行 [order-entry-demo.sql](../../../examples/mini-commerce-spring-boot/scripts/order-entry-demo.sql)：

```sh
docker compose exec -T mysql sh -c 'MYSQL_PWD="$MYSQL_PASSWORD" mysql -u"$MYSQL_USER" "$MYSQL_DATABASE"' < scripts/order-entry-demo.sql
```

脚本使用 `INSERT IGNORE`，补齐客户 301/302、主订单 9001～9004 和以下五条子订单，不重置已有数据：

| 子订单 ID | 主订单 ID | 客户 ID | 商家 ID | 金额 |
| --- | --- | --- | --- | --- |
| 501 | 9001 | 301 | 1001 | 10.00 |
| 502 | 9001 | 301 | 2001 | 20.00 |
| 503 | 9002 | 302 | 1001 | 30.00 |
| 504 | 9003 | 301 | 1001 | 40.00 |
| 505 | 9004 | 302 | 2001 | 50.00 |

主订单 9001 对应两个商家的子订单。两端访问同一批 `merchant_order` 记录，结果按 `id ASC` 排序；初始种子数据的预期结果为：

| 当前身份 | scope | extra filter | 数据 ID | count |
| --- | --- | --- | --- | --- |
| 客户 301 | `customerId=301` | 无 | 501、502、504 | 3 |
| 客户 301 | `customerId=301` | `merchantId=1001` | 501、504 | 2 |
| 客户 301 | `customerId=301` | `merchantId=2001` | 502 | 1 |
| 商家 1001 | `merchantId=1001` | 无 | 501、503、504 | 3 |
| 商家 1001 | `merchantId=1001` | `customerId=301` | 501、504 | 2 |
| 客户 302 | `customerId=302` | 无 | 503、505 | 2 |
| 商家 2001 | `merchantId=2001` | 无 | 502、505 | 2 |

按 [order-entries.http](../../../examples/mini-commerce-spring-boot/requests/order-entries.http) 顺序执行，可对照两端范围、额外筛选、翻页、跨端拒绝、伪造 Header 无效、请求体伪造归属被拒绝和通用路由禁用。例如：

```sh
curl -X POST http://localhost:8082/api/consumer/orders/page \
  -H 'Authorization: Bearer demo-customer-a' \
  -H 'Content-Type: application/json' \
  --data '{"merchantId":1001,"pageNumber":1,"pageSize":20}'
```

成功返回 `CrudResponse<PageResult<CrudRecord>>`。`data.items` 为受 `RETURN` 字段能力约束的记录对象，`data.total=2`，`data.pageNumber=1`，`data.pageSize=20`；客户端直接读取 `data.items`，无需额外的 `data.page` 层。客户 301 不筛选、请求第 2 页且单页 1 条时，返回 502，`total` 仍为 3。

## 5. 拒绝语义与文档来源

| 请求 | 合同结果 |
| --- | --- |
| 缺失或无效凭证、对侧令牌跨端 | 403 |
| `pageNumber=0`、`pageSize=101`、对侧筛选 ID 为负数 | 400 `VALIDATION_ERROR` |
| 用户端请求体传入 `customerId`、商家端传入 `merchantId` | 400 `VALIDATION_ERROR` |
| 合法请求携带伪造的身份或入口 Header | 保留令牌绑定的身份与服务端入口，查询范围不变 |
| 合法筛选在授权范围内无匹配 | 成功，`items=[]`、`total=0` |
| `POST /api/ent-crud/merchantOrder/page` | 404 `ENTITY_NOT_EXPOSED` |

实体文档与定制业务接口各有来源：`/api/ent-doc/contract` 展示 Meta 实体及字段，本轮新增资源 `merchantOrder`，通用 CRUD 禁用不等于实体文档隐藏；两个定制 Controller 的路由、DTO、分页响应及准入说明见本指南和请求文件。示例 DOC 保留原 `local-developer` 暴露配置，两端演示令牌不自动获得实体文档权限。

真实 MySQL 已验证 6 次伪造归属请求体均返回 `400 VALIDATION_ERROR`，仅伪造 Header 仍保持本人授权范围；应用正常关闭，容器、数据卷与网络已清理。最终日志位于 `examples/mini-commerce-spring-boot/target/verification-logs/ent-loom-commerce-verify-1bd3d9f3510f`，完整命令与验证结论统一维护在 G4.32 实施记录。下一小闭环候选是将真实下单流程接入商家子订单生成，待需求授权后确定业务规则与事务边界。
